## 1.13.8 — 금지어 중복 검수 제거와 Jev 대기 제한

수정 요청 한도까지 위반이 남아도 마지막 모델 답변을 그대로 표시합니다. 팝업 없이 감지 목록에 위반이 남았다는 검수 상태만 남기며, 통과로 처리하지 않습니다. 기본 한도는 2회이고 0회는 수정 없이 검수한 답변을 표시합니다. 애매하거나 확신도가 낮은 판정은 수정 대상으로 삼지 않고 답변을 표시합니다. 위반 위치를 확인하지 못한 항목도 수정 대상에서 제외하며, 확인된 대상이 없으면 마지막 답변을 표시합니다. 이때 감지 목록에 상태만 남기고 팝업은 띄우지 않습니다. 완전한 생성 답변을 받은 뒤 Jev 연결·검수 오류가 발생해도 마지막 답변을 표시하며 감지 목록에 검수 건너뜀 상태만 남깁니다. 사용자 중지·채팅 변경·주 생성 모델 오류는 별도로 처리합니다.

Jev 에코 검수 설정은 화면에서 숨기고 실행도 잠시 비활성화했습니다. 기존에 켜 둔 값과 에코 검수 코드는 보존하지만, 그 값 때문에 숨은 검수가 실행되지는 않습니다. **기존 에코 방지 프롬프트 주입은 계속 사용할 수 있습니다.** WEAVE 제목 옆에는 `출처 : 공유달글 weave 프리셋`을 표시합니다.

**기본값은 꺼짐**입니다. 기존 주입 위치와 동작을 유지하고, 사용자가 켠 경우에만 검수합니다.

1. 설정의 **Jev 표시 전 검수**에서 API 키를 입력하고 **연결 확인·저장**을 누릅니다.
2. **답변 표시 전 검수·수정**과 **금지어·금지 구조 검수**를 켭니다.
3. 기본 수정 요청 한도는 **2회**입니다. 첫 답변을 검사하고, 위반 부분의 최소 수정을 최대 2회 요청하며 매번 AI가 작성한 전체 수정 답변을 다시 검사합니다.

`100LOG`와 동일하게 ST의 기존 Chat Completion API에 요청별 custom URL·본문·헤더를 보내 Jev를 호출합니다. **서버 플러그인은 필요 없습니다.** 활성 연결 프로필이나 프리셋 설정은 바꾸지 않습니다. 구형 ST에서 해당 중계가 없는 경우만 직접 연결과 내장 프록시를 순서대로 시도합니다. 내장 프록시가 꺼져 있고 직접 연결도 막힌 경우에는 오류를 표시합니다.

키는 `ttotto.typesafeKey`라는 별도 브라우저 저장값으로 보관합니다. 100LOG·메모리콩의 키를 읽거나 덮어쓰거나 삭제하지 않습니다. 새 브라우저/기기에는 키를 따로 연결해야 합니다. 키는 채팅 메타데이터·확장 설정·검수 기록·콘솔 로그에 저장하지 않습니다. 연결 확인은 작은 Jev 시험 요청 1회를 보냅니다.

### 검수 대기 시간

한 답변의 전체 검수·위반 위치 확인·수정본 재검수에서 **Jev를 기다리는 시간 합계는 최대 10초**입니다. 대기 한도를 넘으면 Jev 요청을 중단하고 최신 완전한 답변을 표시합니다. 감지 목록에 `검수 대기 초과 · 마지막 답변 표시` 상태만 남기고 팝업은 띄우지 않습니다. 늦게 도착한 판정으로 다시 수정하거나 답변을 바꾸지 않습니다. 이 한도는 주 생성 모델이 답변을 작성하거나 재작성하는 시간을 포함하지 않습니다. 실제 전체 응답 지연이 10초로 제한되는 것은 아닙니다. 사용자 중지·채팅 변경 시 결과를 반환하지 않는 동작은 유지합니다.

### inSTead 수정 답변

현재 inSTead는 `generateQuietPrompt`에서 ST의 `Generate(quiet)` 채팅 생성 경로를 사용합니다. Chat Completion에서 현재 채팅 턴을 확인할 수 있으면 또또 주입과, 켜 둔 경우 Jev 검수를 적용합니다. 요청의 `quiet` 유형은 그대로 유지합니다. 번역·generateRaw·Jev 자체 요청은 계속 제외합니다. 두 UI 분기가 공유하는 생성 경로를 모의 호출 체인으로 재현해 검수 켜기·끄기·오류 시 표시를 확인했으며 실제 브라우저에서 두 확장을 함께 생성한 통합 검증은 아닙니다.

### 검수 범위와 응답 처리

- 전역·현재 생성 캐릭터의 금지어와 금지 구조, 실제 주입된 반복 방지 항목을 검사합니다. 다른 캐릭터의 개별 규칙은 해당 캐릭터에게 적용하지 않습니다.
- 정확한 금지어 일치와 해당 문장 위치는 로컬에서 찾으며 이 규칙은 Jev에 다시 보내지 않습니다. 적용 규칙이 정확한 금지어뿐이면 표시 전 검수에서 Jev 호출 없이 코드 검사와 필요한 수정만 수행합니다. 구조·의미 변형은 Jev의 개별 Choice 질문으로 검사하고, 위반 판정 후 문장별 위치 검수를 추가합니다. 초안 전체와 확인된 위반 위치·규칙을 주 생성 모델에 전달해 해당 부분만 최소 수정하도록 요청합니다.
- **주 생성 모델이 일반 답변 형식으로 전체 수정본을 작성합니다. 또또는 문장을 교체하거나 합치지 않습니다.** AI에게 위반 부분만 수정하고 나머지 문장·공백·줄바꿈·태그·패널을 그대로 유지하도록 지시하지만, 원문 보존을 코드로 보장하지는 않습니다. 수정본 전체를 다시 검수한 뒤 통과한 모델 응답을 그대로 반환합니다. 수정 한도에 도달하면 위반이 남아도 마지막 모델 응답을 그대로 반환하며 감지 목록에 상태를 표시합니다. 이전 JSON 교체문 형식만 반환하면 표시를 중단합니다. 위반 위치가 불명확한 항목은 수정 대상에서 제외합니다. 다른 확실한 위치가 있으면 그 부분만 수정하고, 확인된 대상이 없으면 마지막 답변을 표시합니다.
- **메타게이밍·캐릭터 AI화 방지 WEAVE 전문은 Jev에 전송하거나 판정하지 않습니다.** 기존 주입은 유지합니다. 최소 수정 요청은 원래 주 생성 프롬프트와 모델 설정을 유지하고 금지 항목 조건만 수정 사유로 전달합니다.
- Jev 에코 검수는 실행하지 않습니다. 에코 검수용 직전 유저 턴도 Jev에 전달하지 않습니다. 일반 에코 방지 프롬프트의 설정과 주입은 유지합니다.
- normal / regenerate / swipe / continue의 주 생성 요청을 처리합니다. 번역·정밀 분석·100LOG의 Jev 호출 등 보조 요청은 가로채 검수하지 않습니다. 100LOG가 자체적으로 게시하는 숨은 생성 답변도 이 주 생성 검수 범위에 포함하지 않습니다.
- 스트리밍은 켜둬도 되지만 **검수가 끝날 때까지 원문·사고과정·응답 본문을 ST에 돌려주지 않습니다.** 통과, 판정 보류, 위반 위치 미확인, 검수 건너뜀 또는 수정 한도 도달 후 원래 프로토콜의 전체 응답을 반환합니다. 저장·렌더링·번역·스와이프 처리는 ST가 담당합니다. 검사 도중에는 빈 생성 자리나 생성 표시가 보일 수 있습니다.
- **번역 전 원문**을 검사합니다. 답변을 전달한 뒤 번역기가 새로 만든 금지 항목은 검사하지 않습니다.
- 생성 중지, 채팅 변경, 확장/현재 채팅/검수 기능 끄기 시 진행 중 검수와 재작성을 중단합니다. 사용자가 중지한 검수의 초안은 채팅·스와이프에 전달하지 않습니다.
- 수정 한도까지 검수를 마쳤지만 위반이 남으면 마지막 답변을 표시합니다. 별도 팝업은 띄우지 않습니다. 감지 목록에는 `위반 남음 · 마지막 답변 표시` 상태와 위반 항목을 남깁니다. 불명확·최소 확신도 미달 판정은 위반으로 확정하지 않으며, `판정 보류 · 답변 표시` 상태로 답변을 반환합니다. 확인된 수정 위치가 없으면 `위반 위치 미확인 · 마지막 답변 표시` 상태로 반환합니다. 이 둘은 검수 통과로 기록하지 않습니다. 완전한 생성 답변을 받은 뒤 Jev 판정 누락·잘못된 판정 응답·연결 오류·검수 입력 한도 초과가 발생하면 `검수 건너뜀 · 마지막 답변 표시` 상태로 답변을 반환합니다. 이를 검수 통과로 기록하지 않고 팝업도 띄우지 않습니다. 주 생성 모델 오류·불완전한 응답·사용자 중지 시에는 결과를 반환하지 않습니다.
- 단일 텍스트 답변을 지원합니다. 도구 호출·이미지·복수 응답·읽을 수 없는 프로토콜은 표시를 중단합니다. 답변을 잘라 일부만 검사해 통과시키지 않습니다. 검수 입력 한도는 60,000자/128질문, 원본 응답 버퍼 한도는 8MiB입니다. 완전한 생성 답변이 있으면 검수 입력 한도·Jev API 입력 한도 초과 시에도 검수를 건너뛰고 마지막 답변을 표시합니다. 원본 생성 응답 버퍼 한도 초과나 읽을 수 없는 생성 프로토콜은 이 동작에 포함하지 않습니다.
- 의미 위반 위치 검수는 최대 256개의 문장·구간을 대상으로 한 번에 최대 96질문씩 나눠 호출합니다. 긴 규칙 지시문을 문장마다 반복하지 않고 요청 상태에 한 번 담아 참조하며, 60,000자 입력 한도 안에서 자동으로 묶습니다. 정확한 금지어 위치는 이 문장 수 제한 없이 로컬에서 찾습니다. 수정본 전체는 두 경우 모두 다시 검사합니다. 표시 응답의 사용량 정보는 마지막으로 표시한 생성 호출 기준이며 앞선 생성·수정·검수 호출 비용을 합산한 값이 아닙니다.
- 구조 위반은 Jev 확신도 **최소 0.95**이고 위반 위치 역시 이 기준을 충족할 때만 수정합니다. 이전 확신도 저장값이 낮아도 이 구조 기준을 적용합니다. 확신도는 실제 정답률을 뜻하지 않습니다. 기존 확신도 선택기는 숨기고 고정 구조 기준을 안내합니다. 구조 검수는 등록된 조건과 범위 안에서 명백한 위반만 판단하며 비슷한 단어·주제·일상 반응이나 추측만으로 금지 범위를 넓히지 않도록 지시합니다. 조건이 모호하면 해당 판정을 보류하고 답변을 표시합니다. 정확한 금지어 일치 검사는 그대로 유지합니다.

연결 확인·의미 검수·의미 위반 위치 검수에는 Jev 비용이 발생하고, 수정 요청에는 현재 주 생성 모델 비용이 추가됩니다. 검수 기능을 끄면 이 기능의 Jev·수정 요청 호출은 없습니다. 기존 정밀 분석·드래그 보조 AI 비용은 별도입니다.

GitHub로 설치한 사용자는 실리태번 확장 목록에서 또또를 업데이트한 뒤 브라우저를 새로고침하고 1.13.8을 확인하세요. ZIP으로 직접 설치할 때는 기존 `ttotto` 폴더 안의 `.git`을 유지하고 코드 파일만 덮어쓰세요. 실제 ST/번역기/모델 조합으로 검수 켜기·재생성·중지 동작을 확인해야 합니다.

## 1.12.9 depth 0 보충 위치 수정

- 기존 `depth_0` 설정값을 유지하면서 화면 설명을 **채팅 히스토리 끝 (기존 depth 0)**으로 명확히 했습니다. 이 설정은 작가노트 전용 위치가 아닙니다.
- 등록된 또또 본문을 최종 요청에서 찾지 못했을 때, 예전에는 전체 전송 메시지 맨 끝에 보충했습니다. 이제 실제 채팅 턴과 전송 메시지를 대조해 **히스토리 바로 뒤, 후속 프리셋·새 assistant 프리필·CardInject 최종 지시문보다 앞**에 보충합니다.
- continue에서는 실제 마지막 assistant 기록을, 재생성에서는 요청에 남아 있는 실제 턴을 기준으로 합니다. 이름 접두사, 알려진 번역 원문, 멀티모달 텍스트와 생성 시작 시 저장한 턴도 지원합니다. 숨긴 메시지나 새 프리필을 채팅 기록으로 가정하지 않습니다.
- 이미 주입된 본문은 이동하거나 삭제하지 않습니다. 위치를 유일하게 확인할 수 없으면 기존 내용을 보존하고 콘솔 경고와 함께 마지막에 보충합니다. 프리셋 대상 찾기 실패의 기존 최종 보충 경로는 별도로 유지합니다.
- 기존 위치 설정, 금지어·에코 순서와 WEAVE 한 세트 구성, 두 원본 프롬프트 전문, 별 안내 문구, 저장된 프리셋과 채팅, 다른 확장 설정을 유지합니다. 같이 제공하는 CardInject 1.0.6에는 중간 재작성 후 자기 최종 지시문이 중복되던 경우도 수정했습니다.
- ZIP 안 파일 전체를 기존 또또 폴더 안에 덮어쓰고 페이지를 새로고침하세요. 새 `history-position.js`도 필요합니다. 기존 `.git` 폴더는 유지하세요.

소스와 ZIP 압축 해제본에서 각각 자체 검사 71개와 별도 CardInject 1.0.6 동시 사용 검사 5개를 통과했습니다. 동시 사용 검사는 두 로드 순서 및 프리셋 상대 위치/depth 0 조합마다 200회 생성하며, 조립 이벤트를 거치는 요청과 fetch 보충만 거치는 요청, 중간 재작성 후 재보충, 프리셋·채팅·다른 확장 설정 보존과 비활성화를 포함합니다. 코드와 모의 ST 요청 기준이며 사용자 환경에서 실제 모델 응답을 생성한 검증은 아닙니다.

- 같은 이름의 캐릭터도 고유 식별자로 엄격하게 분리
- 반복된 실제 예문과 메시지 위치 확인
- 다음 생성 한 번에만 또또를 쉬게 하는 기능

- 좁은 모바일 화면에서도 팝업 바깥 배치를 건드리지 않는 세로 전용 설정 스크롤

## 또또는 어떻게 작동하나요?

또또의 기본 동작은 다음과 같습니다.

1. 사용자가 메시지를 보냅니다.
2. 에코 방지가 켜져 있으면 사용자 메시지를 되풀이하지 말라는 지시를 생성 직전에 추가합니다.
3. 자동 감지 결과와 직접 금지어도 같은 생성 프롬프트에 추가합니다.
4. 캐릭터가 답변을 생성합니다.
5. 또또가 번역문이 아닌 실리태번 원문을 저장합니다.
6. 최근 캐릭터 답변 중 설정된 범위만 불러옵니다.
7. 인포패널과 HTML 등 분석 제외 영역을 제거합니다.
8. 남은 대사와 지문에서 반복되는 표현과 구조를 찾습니다.
9. 허용한 표현은 결과에서 제외하고, 새 답변에 맞춰 분석 범위를 갱신합니다.

또또는 채팅 전체를 백그라운드에서 계속 훑지 않습니다. 필요한 시점에 최근 범위만 확인하며, 화면이 다시 그려질 때마다 전체 분석을 반복하지 않습니다.

### 주입 확인

브라우저 콘솔의 `[🌀또또] 전송 직전 태그 검사`를 펼치면 다음을 확인할 수 있습니다.

- `mainRequestMatched: true`: 본생성 진행 상태와 실제 채팅 메시지 대조를 통과함
- `metagaming: true`, `characterAi: true`: 해당 시점의 전송 본문에 두 원본 태그가 있음
- `fallbackUsed: false`: 프리셋 대상 누락 경고가 없음. 이미 존재하는 본문은 그대로 유지함
- `fallbackUsed: true`: 일부 프리셋 대상을 찾지 못함. `fallback`에서 항목과 실패 이유를 확인할 수 있으며 누락된 본문만 답변 직전에 보충함

`type`이 없거나 `normal`이라는 이유만으로 본생성으로 간주하지 않습니다. 본생성 진행 상태와 마지막 실제 채팅 턴의 전체 텍스트(알려진 원문·번역문 포함)를 대조합니다.

일부 답변 처리 확장은 본답변도 `type: quiet`으로 전송합니다. 이 경우 가장 가까운 `sendOpenAIRequest`의 호출자가 ST의 `sendGenerationRequest` 또는 `finishGenerating`인지 확인하고, 실제 채팅 메시지도 일치할 때 주입합니다. `generateRawData`, `generateQuietPrompt`, `custom-request.js` 등의 보조 전송 경로는 계속 제외합니다. 바깥 호출 경로에 번역기 이름이 있다는 이유만으로 본생성을 제외하지 않습니다. 요청의 `type`, 모델·연결 프로필·스트리밍 설정은 변경하지 않습니다.

`requestPath: st-main-generation`은 본생성 호출 경로 확인, `requestPath: confirmed-main-request`는 요청 준비 단계에서 확인한 동일 전송 본문의 재확인을 의미합니다. 확인 기록은 현재 생성 동안만 유지됩니다. 다른 확장이 함수명을 바꾸거나 본답변과 보조 요청을 같은 경로·본문으로 보내면 추가 호환 처리가 필요할 수 있습니다.

현재 채팅과 내용이 같고 생성 중이라는 사실만으로는 보조 요청에 주입하지 않습니다. 본생성 호출 경로나 이미 확인한 요청 본문이 필요합니다.

프리셋 원본 설정이나 채팅 기록을 수정하지 않고, 전송용 `messages` 사본만 변경합니다. `fetch(url, options)`와 `fetch(Request)`를 모두 지원하며, ST의 매크로 처리 결과와 프리셋 본문을 사용해 위치를 찾습니다. 프리셋이 한 메시지에 합쳐져 있으면 선택한 항목의 본문 경계에서 나눠 삽입합니다. 빈 항목, 비활성 항목, 동일 본문이 여러 번 나타나는 모호한 위치나 다른 확장이 완전히 다시 쓴 프리셋은 위치를 확정하지 못할 수 있습니다.

이 로그는 또또 훅이 다음 전송 함수로 넘기기 직전의 상태이며 서버 수신 확인은 아닙니다. 다른 확장이 이후 요청을 변경하거나 별도로 캡처한 전송 함수를 사용하면 전송 직전 훅을 우회할 수 있습니다. 최종 전송 내용은 Network의 해당 본 답변 `generate` 요청에서 확인하세요. 보조 요청도 같은 URL을 사용할 수 있으므로 이름만으로 구분하지 마세요.

## 프리셋 순서와 확장 간섭

또또는 프리셋의 `prompts`와 `prompt_order`를 읽기만 합니다. 원본 순서·내용·활성 상태를 재정렬하거나 저장하지 않으며, 위치 선택은 전송용 메시지에 또또 내용을 추가하는 데만 사용합니다. 이미 존재하는 프롬프트 본문은 삭제하거나 다른 위치로 옮기지 않습니다. 사용자 메시지에 인용된 주입문은 그대로 두고, 시스템 지시가 이미 들어갔다고 오인하지 않습니다.

CardInject와 함께 사용할 때 전송 훅과 매크로 관찰 훅이 생성마다 겹쳐 쌓이지 않도록 서로의 연결을 인식합니다. 다른 확장의 전송 함수를 유지하며, 비활성화 때는 또또 이름의 주입 항목만 정리하고 연결된 다른 확장의 훅은 제거하지 않습니다. 같은 기준 프롬프트에 여러 확장이 내용을 추가하면 추가 내용끼리의 순서는 확장 실행 순서에 따라 달라질 수 있습니다. 프리셋 자체의 저장 순서는 바뀌지 않습니다.

ZIP 패치 설치 시 기존 설치 폴더에 포함 파일을 모두 덮어쓰세요. 새 `hook-chain.js`도 필요하므로 `index.js`만 교체하면 안 됩니다. 기존 `.git` 폴더를 유지하고 페이지를 새로고침하세요.

## 무엇을 분석하나요?

또또는 **캐릭터가 출력한 답변 원문**을 분석합니다.

- 사용자 메시지: 분석하지 않음
- 번역기가 만든 한국어 표시문: 분석하지 않음

- 여러 스와이프 중 현재 선택된 답변: 분석함
- 원본이 영어인 답변: 영어로 분석함
- 처음부터 한국어로 생성된 답변: 한국어로 분석함

따라서 영어로 생성한 뒤 번역기를 사용하는 경우에도 한국어 번역 때문에 반복 분석 결과가 왜곡되지 않습니다.

## 직전 유저 말 되받기·에코 방지

에코 방지는 캐릭터가 직전 사용자 대사의 일부를 의문형·인용형·감탄형으로 받아치거나, 사용자 메시지의 대사·행동·묘사를 단어만 바꿔 다시 서술하는 현상을 줄입니다. 일반 방지 규칙과 함께, 직전 유저 원문의 명시적인 따옴표 대사에서 짧은 핵심 구절을 로컬 규칙으로 뽑아 이번 답변에만 적용되는 임시 에코 금지 목록으로 추가합니다. 특정 예시 단어나 `X` 같은 대체 기호는 사용하지 않습니다.

- 마지막 단어·구절을 의문형이나 짧은 감탄으로 되받지 않음
- `~라`, `~라고?`, `~라니` 같은 인용형 대사로 답변을 시작하지 않음
- 사용자가 한 내용은 이미 일어난 사실로 취급
- 같은 문장을 그대로 복사하거나 번역해서 되풀이하지 않음
- 동의어, 문장 순서 변경, 시점 변경을 이용한 유사 재서술도 피함
- 사용자의 내용을 무시하지 않고 그에 대한 새로운 반응·대사·행동부터 이어감
- 출력 전 캐릭터 대사 전체를 직전 사용자 대사와 대조하고, 일부라도 그대로 반복하거나 직접 바꿔 말한 줄은 다시 작성
- `"..."`, `“...”`, `‘...’`, `「...」`, `『...』` 안의 대사만 임시 구절 추출 대상으로 사용
- 평문·행동·서술·OOC·태그·인포블럭은 임시 구절로 추측하지 않음
- 임시 구절은 다음 유저 메시지가 오면 새 목록으로 교체되며 지난 목록은 남지 않음

설정의 **에코 방지 강화 모드**를 켜면 임시 금지 구절을 최대 8개까지 사용하고, 에코가 포함된 답변 전체를 무효로 취급해 출력 전에 다시 쓰도록 더 강하게 지시합니다. 첫 서술과 첫 대사부터 새로운 반응·결과·행동으로 이어지게 하며, 대사와 서술을 나눠 두 번 검사하도록 요구합니다. 강화 모드는 기본적으로 꺼져 있습니다.

설정의 **금지어들 방지 강화 모드**를 켜면 전역·캐릭터별 금지어와 전역·캐릭터별 구조 금지를 모두 강화합니다. 등록된 표현이나 구조를 하나라도 위반한 답변 전체를 무효로 취급하고, 출력 전에 대사와 서술을 차례로 검사해 위반 문장을 다시 쓰도록 지시합니다. 별도 API 호출은 없습니다. 현재 생성에 적용되는 영구 항목은 30개로 잘리지 않고 모두 전달되며, 일반 금지어는 공통 규칙을 한 번만 쓰고 압축 목록으로 묶어 중복 토큰을 줄입니다. 항목이 많아질수록 목록과 개별 구조 지시문의 입력 토큰은 증가합니다. 강화 모드는 기본적으로 꺼져 있습니다.

설정의 **드래그 금지 메뉴 표시**를 끄면 AI 답변을 드래그했을 때 나타나는 `표현 / 구조` 빠른 등록 메뉴가 비활성화됩니다. 이때 관련 `mouseup`, `touchend`, `selectionchange` 감시도 함께 해제되며, 다시 켜면 즉시 복구됩니다. 기본값은 켜짐입니다.

전역 금지어는 예외 없이 모든 캐릭터에 적용됩니다. 같은 단어는 캐릭터별 영구 금지어와 중복 저장되지 않으며, 전역으로 등록하면 모든 UUID에 남아 있던 동일 캐릭터별 항목을 자동 정리합니다. 이미 전역인 단어를 캐릭터별로 다시 추가할 수도 없습니다. 감지 목록의 **전역 금지 삭제**와 설정의 **삭제**는 전역 원본을 제거하여 모든 캐릭터에서 해제하고, 캐릭터별 **영구 금지 해제**는 해당 UUID의 항목만 제거합니다.

이 기능은 사용자 메시지를 별도로 AI에게 분석시키지 않습니다. 따옴표 대사와 핵심 구절은 브라우저 안의 자바스크립트 규칙으로 처리하고 생성 요청에 짧은 방지 지시를 추가할 뿐이므로 **추가 API 호출은 없으며**, AI 정밀 분석을 꺼도 작동합니다. 임시 목록이 포함된 만큼 본 생성 요청의 입력 토큰만 소량 늘어날 수 있습니다. 이어쓰기에는 적용하지 않아 이미 생성된 캐릭터 답변의 흐름을 방해하지 않습니다.

## 최근 메시지 분석 범위

기본 분석 범위는 최근 캐릭터 답변 20개입니다. 설정에 따라 분석 범위를 변경할 수 있습니다.

예를 들어 답변이 20개인 상태에서 새 답변이 들어오면 다음처럼 움직입니다.

```text
#1 ~ #20 분석
새 답변 #21 생성
#1은 분석 범위에서 제외
#2 ~ #21 분석
```

분석 범위 밖으로 밀려난 표현은 자동 반복 감지에서 사라질 수 있습니다. 그러나 다음 항목은 최근 메시지 범위와 별도로 저장됩니다.

- 사용자가 직접 등록한 금지어
- 사용자가 허용한 표현
- 캐릭터별 설정
- 선택적으로 저장한 과거 채팅 기억

기본 설정에서 필요한 답변이 아직 충분히 쌓이지 않았다면 수집 중 또는 분석 대기 상태로 표시될 수 있습니다. **직접 금지어는 자동 분석 대기와 관계없이 적용됩니다.**

## 어떤 반복을 찾나요?

### 1. 반복 문구

```text
Kieran reached out and caught her wrist.
Kieran reached out and lifted her chin.
Kieran reached out and closed the door.
```

`Kieran reached out`처럼 여러 답변에서 되풀이되는 문구를 찾습니다.

### 2. 반복되는 문장 시작과 마무리

```text
You want me to leave?
You want me to believe that?
You want me to apologize?
```

내용이 달라도 동일한 방식으로 대사를 시작하는 습관을 반복 후보로 볼 수 있습니다.

### 3. 반복 문장 구조

```text
It wasn't anger. It was fear.
It wasn't jealousy. It was concern.
It wasn't a request. It was an order.
```

각 문장의 핵심 단어는 다르지만 모두 아래 구조를 사용합니다.

```text
It wasn't A. It was B.
```

또또는 이처럼 겉에 들어가는 단어가 달라도 문장 틀이 반복되는 경우를 찾을 수 있습니다.

다만 다음처럼 뜻은 같지만 문법과 표현이 완전히 달라지면 기본 분석이 놓칠 수 있습니다.

```text
He had mistaken the feeling for anger, although fear was what truly lay underneath.
```

이러한 의미 단위의 변형까지 더 넓게 찾고 싶다면 AI 정밀 분석을 사용하세요.

### 4. 반복 행동과 신체 묘사

다음과 같은 행동이 표현만 조금씩 바뀐 채 계속 사용되는지도 확인합니다.

- 손을 뻗어 손목을 잡음
- 목소리를 낮추거나 거칠게 만듦
- 턱을 굳힘
- 숨을 삼킴
- 입꼬리를 올리거나 비웃음
- 시선을 고정함

기본 분석은 표현의 형태가 비슷할수록 잘 찾습니다. 의미는 비슷하지만 단어와 문법이 크게 달라지면 감지하지 못할 수 있습니다.

### 5. 반복 대사

같은 질문, 추궁, 부정, 호칭이나 짧은 추임새가 반복되는 경우도 대사 반복 후보로 감지합니다. 대사와 지문은 구분하여 분석되므로 동일한 단어가 서로 다른 용도로 사용된 경우의 오탐을 줄입니다.

## 자동 반복 감지와 직접 금지어의 차이

두 기능은 완전히 별개입니다.

| 구분 | 자동 반복 감지 | 직접 금지어 |
| --- | --- | --- |
| 등록 방법 | 최근 답변을 분석해 자동 발견 | 사용자가 직접 입력 |
| 적용 기간 | 최근 분석 범위에 따라 바뀜 | 삭제하기 전까지 유지 |
| 반복 필요 여부 | 여러 번 사용되어야 감지됨 | 한 번도 나오지 않아도 적용 |
| 적용 대상 | 반복 문구·구조·습관 | 사용자가 입력한 표현 |
| 캐릭터 구분 | 캐릭터별 | 캐릭터별 |

예를 들어 다음을 직접 금지어로 등록했다면:

```text
BLONDE
SIX-FOOT-FOUR-FRAME
```

이 표현들은 최근 답변에서 발견되지 않더라도 다음 생성 때 계속 금지 목록으로 전달됩니다.

직접 금지어는 주로 입력한 표현 자체를 대상으로 합니다. `BLONDE`를 등록했다고 해서 아래처럼 의미가 비슷한 모든 표현이 자동으로 금지되는 것은 아닙니다.

```text
fair-haired man
golden-haired athlete
the light-haired swimmer
```

같이 막아야 하는 변형 표현은 별도로 등록하는 것이 가장 확실합니다. 대소문자는 같은 표현으로 처리되지만, 띄어쓰기·하이픈·철자·동의어가 크게 달라진 표현은 별개의 문구로 판단될 수 있습니다.

## 직접 금지어 사용법

1. 또또 설정에서 직접 금지어 목록을 엽니다.
2. 피하고 싶은 단어나 문구를 입력합니다.
3. 현재 캐릭터에 저장합니다.
4. 다음 생성부터 해당 캐릭터의 금지 지시에 포함됩니다.

직접 금지어는 자동 반복 패턴의 최대 표시 개수와 별도로 주입됩니다. 금지어가 실제 답변 본문에 다시 출력되면 `🔥 본문 N개 답변`과 근거 문구로 확인할 수 있습니다. 근거 문구를 누르면 해당 메시지로 이동합니다.

불꽃 기록은 답변이 화면에 렌더링된 뒤 현재 메시지와 스와이프에 연결해 저장합니다. 실리태번에 저장된 원문에서 인포패널·HTML/태그 블록·숨겨진 사고과정·코드 블록을 항상 제외한 뒤, 등록한 단어나 문구가 독립된 표현으로 실제 남아 있을 때만 셉니다. 이 제외 기준은 반복 분석의 태그 설정과 무관하게 강제 적용됩니다. 번역기가 만든 화면 표시문, `anchor`에 대한 `anchored` 같은 단순 부분문자열, 중복 렌더링 이벤트는 세지 않습니다. 한국어 명사는 `포식자가`, `포식자처럼`처럼 조사가 붙은 정상 형태도 같은 표현으로 인식합니다.

메시지를 수정해 금지어를 지우거나 삭제하거나 다른 스와이프로 바꾸면 연결된 위반 기록도 제거됩니다. 각 금지어의 `초기화` 또는 설정 하단의 `위반 기록 전체 초기화`는 숫자와 근거만 지우며 금지어 자체는 유지합니다. 금지어를 삭제했다 다시 등록하면 새 기록으로 시작합니다. v1.8.8 이하에서 잘못 집계된 기존 횟수는 v1.8.9 최초 실행 시 자동으로 폐기됩니다.

직접 금지어는 이미 생성된 과거 메시지를 수정하지 않습니다. 등록한 뒤 생성되는 답변부터 영향을 줍니다.

> 직접 금지어 역시 프롬프트 지시 방식입니다. 모델이 지시를 무시하면 다시 등장할 수 있으며, 이 경우 답변을 재생성하거나 변형 표현을 추가로 등록하세요.

## 허용 처리

반복 감지 목록에 나타났지만 계속 사용되어야 하는 표현은 허용할 수 있습니다.

예시:

- 매 답변에 필요한 고정 문구
- 캐릭터의 필수 호칭
- 특정 형식의 상태 표시
- 의도적으로 반복하는 대사

허용한 표현은 이후 반복 감지 대상에서 제외됩니다. 허용 상태 역시 캐릭터의 고유 식별자를 기준으로 저장됩니다.

직접 금지어와 허용 목록에 같은 표현을 동시에 넣지 않는 것을 권장합니다. 결과가 예상과 다를 경우 두 목록을 모두 확인하세요.

## 캐릭터 구분 방식

또또는 표시 이름이 아니라 캐릭터 카드의 고유 식별자를 기준으로 설정을 분리합니다.

이름이 동일한 캐릭터 카드가 여러 개 있어도 서로 다른 캐릭터로 취급됩니다.

```text
김홍진 카드 A → UUID A
김홍진 카드 B → UUID B
```

카드 A의 금지어·허용 표현·분석 기록은 카드 B에 적용되지 않습니다. 반대로 동일한 캐릭터 UUID의 과거 채팅 기억을 공유하도록 설정하면 같은 캐릭터의 다른 채팅을 참고할 수 있습니다.

## 분석 제외 블록

날짜, 날씨, 장소를 표시하는 인포패널이나 채팅 꾸미기용 HTML은 반복 분석에서 제외할 수 있습니다.

### 모든 태그 블록 제외

이 옵션을 켜면 다음처럼 짝을 이루는 태그 내부를 통째로 분석에서 제외합니다.

```html
<Info_panel>
[Date: 2026.08.16.]
[Weather: Clear | 20°C]
[Location: Bedroom]
</Info_panel>
```

```html
<div class="info-card">
    ...
</div>
```

인포패널 형식이 달라지더라도 태그 안에 들어 있다면 반복 분석에 포함되지 않습니다. 이 제외는 또또 내부에서만 조용히 처리되며, 생성 AI에게 인포블럭·태그·HTML에 관한 지시를 추가하지 않습니다. 따라서 블록 출력은 기존 프리셋의 서식 지시만 따릅니다.

### 제외 태그

특정 태그의 내부만 제외할 때 사용합니다.

입력 예시:

```text
Info_panel
Info_block
style
```

`<`와 `>`를 제외한 태그 이름만 입력하는 것을 권장합니다.

### 제외 클래스

특정 HTML 클래스를 사용하는 블록만 제외할 때 사용합니다.

HTML이 다음과 같다면:

```html
<div class="info-card">...</div>
```

제외 클래스에는 다음처럼 입력합니다.

```text
info-card
```

점(`.`)을 붙이지 않은 클래스 이름만 입력하는 것을 권장합니다.

### 태그와 클래스의 차이

- 태그 제외: `<Info_panel>`, `<style>`, `<div>`처럼 태그 이름을 기준으로 제외
- 클래스 제외: `<div class="info-card">`처럼 `class` 이름을 기준으로 제외

모든 `<div>`를 제외하면 일반 채팅 장식까지 넓게 제외될 수 있으므로, 가능한 경우 `info-card`처럼 구체적인 클래스를 등록하는 것을 권장합니다.

## AI 정밀 분석

기본 반복 분석은 빠르게 작동하며 별도의 AI 호출 없이 문구와 구조를 비교합니다.

AI 정밀 분석을 사용하면 다음과 같은 반복을 더 넓게 찾을 수 있습니다.

- 단어가 다르지만 의미가 비슷한 행동
- 문법이 달라도 같은 기능을 하는 대사
- 계속 반복되는 감정 전개
- 표현만 바뀐 동일한 신체 반응
- `A가 아니라 B였다`처럼 반복되는 서술 습관의 변형

정밀 분석을 켠 경우 선택한 연결 프로필을 사용하며, 정리된 원문이 해당 AI 요청에 포함될 수 있습니다. 사용한 API 또는 연결 방식에 따라 비용이 발생할 수 있습니다.

긴 채팅에서 속도가 중요하다면 기본 분석만 사용하거나 정밀 분석의 실행 간격을 늘리세요.

## 과거 채팅 기억

과거 채팅 기억을 켜면 동일한 캐릭터 UUID의 다른 채팅에서 저장한 최근 원문도 참고할 수 있습니다.

- 동일한 캐릭터 UUID만 공유
- 이름이 같은 다른 카드와는 공유하지 않음
- 최근 원문을 제한된 개수만 저장
- 필요할 때 사용자가 직접 기억 삭제 가능

이 옵션을 끄면 현재 채팅의 최근 분석 범위만 사용합니다.

## 다음 생성에서만 쉬기

`다음 생성에서만 또또 쉬기`를 누르면 다음 생성 한 번에만 또또의 주입을 건너뜁니다.

그다음 생성부터는 자동으로 다시 활성화됩니다. 특정 장면에서 의도적인 반복을 한 번 허용하고 싶을 때 사용할 수 있습니다.

---

## 적용되는 생성

또또는 일반적인 캐릭터 답변 생성에 맞춰 작동합니다.

- 일반 생성
- 재생성
- 스와이프 생성
- 이어쓰기

조용한 생성이나 사용자 대필처럼 캐릭터 답변 반복 방지와 무관한 요청에는 적용되지 않도록 구분됩니다.

---

## 주입문 보기

주입문 보기에서는 또또가 자동으로 감지한 반복 패턴과 현재 적용 상태를 확인할 수 있습니다.

우측 상단에는 현재 주입문의 글자 수와 실리태번의 현재 토크나이저로 계산한 토큰 수가 함께 표시됩니다. 토크나이저를 사용할 수 없는 경우에만 근삿값을 표시하며, 토큰 계산 자체는 API를 호출하지 않습니다.

직접 금지어는 자동 감지 결과와 별도로 관리되므로, 자동 분석 주입문 목록에 나타나지 않을 수 있습니다. 직접 금지어의 적용 여부는 **직접 금지어 목록**에서 확인하세요.

주입문 보기는 분석 결과를 점검하는 기능이며, 캐릭터 카드나 로어북 자체를 수정하지 않습니다.

## 성능과 렉

또또는 다음 방식으로 불필요한 부하를 줄입니다.

- 채팅 전체가 아닌 최근 설정 범위만 분석
- 분석 결과 캐시 사용
- 짧은 시간 동안 여러 이벤트가 발생하면 묶어서 처리
- 메시지 화면이 다시 그려질 때마다 분석하지 않음
- 백그라운드 무한 반복 작업을 사용하지 않음
- 긴 채팅에서도 오래된 메시지를 매번 다시 읽지 않음

렉이 느껴진다면 다음을 확인하세요.

1. 분석 범위를 줄입니다.
2. AI 정밀 분석을 끄거나 실행 간격을 늘립니다.
3. 과거 채팅 기억을 잠시 끕니다.
4. 또또와 실리태번을 최신 상태로 다시 불러옵니다.

## 자주 묻는 질문

### Q. 정확히 같은 단어가 아니어도 반복 구조를 찾나요?

찾을 수 있습니다. `It wasn't A. It was B.`처럼 내용만 바뀌고 문장 틀이 반복되는 경우가 대표적입니다. 다만 문법과 단어가 완전히 달라지면 기본 분석이 놓칠 수 있으며, 이런 경우 AI 정밀 분석이 더 적합합니다.

### Q. 최근 20개 밖으로 밀려난 반복은 어떻게 되나요?

자동 반복 후보에서는 사라질 수 있습니다. 계속 막고 싶은 표현은 직접 금지어로 등록하세요.

### Q. 직접 금지어도 20개가 지나면 사라지나요?

아니요. 직접 삭제하기 전까지 해당 캐릭터에 계속 적용됩니다.

### Q. 금지어를 등록했는데 다시 나왔어요.

기본 모드는 프롬프트 주입 방식이므로 모델이 지시를 무시하거나 다른 철자·동의어로 우회할 수 있습니다. 해당 변형도 등록하고 재생성하세요. Jev 표시 전 검수를 켠 경우에는 위반 부분의 최소 수정을 요청하고 다시 검수합니다. 수정 한도까지 위반이 남으면 마지막 답변을 표시하고 감지 목록에 상태를 남깁니다. 의미 판정의 미탐이나 검수 후 번역에서 생긴 표현도 남을 수 있습니다.

### Q. 번역된 한국어 때문에 반복으로 잡힐 수 있나요?

또또는 번역 표시문이 아니라 실리태번 원문을 기준으로 분석합니다. 원문이 영어라면 영어만 분석합니다.

### Q. 원본 답변 자체가 한국어라면요?

처음 생성되어 실리태번에 저장된 원문이 한국어라면 한국어로 분석합니다.

### Q. 인포패널이 반복으로 잡혀요.

모든 태그 블록 제외를 켜고, 사용하는 태그나 클래스를 분석 제외 목록에 등록하세요. `Info_panel`, `Info_block`, `info-card` 등이 대표적인 예시입니다.

### Q. 이름이 같은 캐릭터끼리 설정이 섞이나요?

섞이지 않습니다. 캐릭터의 고유 식별자를 기준으로 구분합니다.

### Q. 또또가 기존 메시지를 수정하나요?

수정하지 않습니다. 다음 답변을 생성할 때 반복 방지 지시를 추가할 뿐입니다.

### Q. 또또를 켜면 항상 백그라운드에서 분석하나요?

아니요. 상시 무한 분석을 하지 않으며, 필요한 시점에 최근 범위와 변경된 데이터만 확인합니다.

### Q. 에코 방지는 API를 호출하나요?

기존 에코 방지 주입은 추가 호출이 없습니다. Jev 에코 검수는 현재 숨김·비활성 상태입니다. 별도의 금지 항목 표시 전 검수를 켜면 그 검수에 Jev 호출이, 위반 부분의 최소 수정 요청에 주 생성 모델 호출이 추가됩니다.

## 권장 설정

처음 사용하는 경우 다음 설정을 권장합니다.

- 최근 분석 범위: 20개
- 모든 태그·HTML 블록 제외: 켜기
- 인포패널 태그와 클래스: 사용하는 형식에 맞게 등록
- AI 정밀 분석: 우선 끄고 사용한 뒤 필요할 때 켜기
- 과거 채팅 기억: 현재 채팅만 볼 때는 끄기
- 직전 유저 메시지 에코 방지: 켜기
- 계속 보기 싫은 표현: 직접 금지어로 등록
- 의도적으로 반복해야 하는 표현: 허용 처리

## 알아두세요

- 또또는 AI의 출력 다양성을 돕는 확장이지 문법 검사기나 검열 필터가 아닙니다.
- 반복 감지는 완벽하지 않으며 모델, 프리셋, 답변 길이와 문체에 따라 결과가 달라집니다.
- 직접 금지어는 단어의 모든 동의어와 변형을 자동으로 금지하지 않습니다.
- 너무 많은 금지 지시는 답변을 부자연스럽게 만들거나 다른 표현의 반복을 유발할 수 있습니다.
- 필요한 표현은 허용하고, 정말 싫은 표현만 직접 금지어로 등록하는 것을 권장합니다.
